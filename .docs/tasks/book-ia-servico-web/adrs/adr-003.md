# ADR-003: Modelos de Dados — Recriação do Esquema PostgreSQL com SQLAlchemy

## Status

Aceito

## Data

2026-05-25

## Contexto

O esquema original do Book-IA (Delphi) existe apenas na DAO em Delphi (`DAO.Leitor.Book.pas`). Os arquivos SQL originais foram perdidos. A migração para Python exige recriar toda a estrutura do banco do zero, usando SQLAlchemy + Alembic para versionamento.

O esquema atual tem 7 tabelas: `TB_LIVROCABECALHO`, `TB_LIVROPAGINA`, `TB_LIVROPERSONAGENS`, `TB_LIVROFALAS`, `TB_LIVROARQUIVOS`, `TB_LIVROAPIS`, `TB_LIVROVOZES`.

## Decisão

Recriar o esquema PostgreSQL com as seguintes alterações em relação ao original:

- **Nomeclatura:** tabelas e colunas em snake_case (sem prefixo TB_). Exemplo: `livro` ao invés de `TB_LIVROCABECALHO`.
- **ORM:** SQLAlchemy 2.0 com estilo declarativo. Migrations gerenciadas por Alembic.
- **ID:** `id` (Integer, PK, auto-increment) ao invés de `CD_SEQUENCIAL`.
- **Timestamps:** Colunas `created_at` e `updated_at` automáticas em todas as tabelas.
- **Chaves estrangeiras:** explícitas com SQLAlchemy `ForeignKey`.
- **Índices:** índices em todas as colunas usadas em JOINs e WHERE frequentes.
- **Textos longos:** `SQLAlchemy TEXT` para TX_PAGINA e TX_FALA (conteúdo extenso).
- **Armazenamento de áudios:** apenas caminhos no banco; arquivos no sistema de arquivos local.

### Tabelas recriadas

| Delphi (Original) | SQLAlchemy (Novo) | Notas |
|---|---|---|
| TB_LIVROCABECALHO | `livro` | Metadados do livro, status do pipeline |
| TB_LIVROPAGINA | `pagina` | Texto por página |
| TB_LIVROPERSONAGENS | `personagem` | Personagens identificados, perfis, vozes |
| TB_LIVROFALAS | `falas` | Mapeamento fala → personagem → página |
| TB_LIVROARQUIVOS | `arquivo` | Referências a PDFs e arquivos de áudio |
| TB_LIVROAPIS | `api_config` | Configurações de APIs (LLM, TTS, MusicGen) |
| TB_LIVROVOZES | `voz` | Banco de vozes disponíveis |

### Tabelas novas

| Tabela | Finalidade |
|---|---|
| `usuario` | Autenticação (login, hash de senha, perfil) |
| `sessao` | Sessões de login (session-based auth) |
| `book_task` | Fila de processamento (status, prioridade, progresso) |
| `book_review` | Revisão de personagens (Fase 3) |

## Alternativas Consideradas

### Alternativa 1: Manter nomeclatura Delphi (TB_LIVROCABECALHO)

- **Descrição**: Preservar nomes originais para compatibilidade
- **Prós**: Familiar para quem conhece o Delphi
- **Contras**: Nomeclatura inconsistente com Python conventions (snake_case); prefixo TB_ redundante em SQLAlchemy
- **Por que rejeitada**: Convenções Python são claras. Nomes em snake_case sem prefixo são mais legíveis.

### Alternativa 2: SQLite para MVP

- **Descrição**: Usar SQLite inicialmente, migrar para PostgreSQL depois
- **Prós**: Zero configuração no MVP
- **Contras**: Migrar depois exige recriar todo o banco; SQLite não supora concorrência de escrita bem como PostgreSQL; Celery com SQLite é problemático
- **Por que rejeitada**: PostgreSQL é a escolha certa desde o início. Celery + SQLite não é recomendado. O custo de setup é mínimo.

## Consequências

### Positivas

- Migrações versionadas (Alembic) permitem rastreabilidade e rollback.
- Nomeclatura Python-friendly facilita manutenção.
- Tabelas novas (usuario, book_task) preparam o terreno para autenticação e filas.
- SQLAlchemy ORM elimina a necessidade do Delphi DAO.

### Negativas

- Recriação completa do banco exige script de seed para vozes e dados iniciais.
- Mudança de nome de colunas (CD_SEQUENCIAL → id) requer mapeamento cuidadoso.

### Riscos

- **Risco**: Volume de texto em páginas grandes pode exceder limites do PostgreSQL TEXT.
- **Mitigação**: PostgreSQL TEXT suporta até 1 GB; sem risco prático.
