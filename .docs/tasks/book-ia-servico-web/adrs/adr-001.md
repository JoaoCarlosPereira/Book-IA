# ADR-001: Estratégia de Entrega Faseada com MVP Vertical

## Status

Aceito

## Data

2026-05-25

## Contexto

O Book-IA é um serviço web para processamento de PDFs e geração de audiobooks com IA. O escopo é amplo: inclui múltiplos tipos de conteúdo, níveis de produção configuráveis, revisão colaborativa de personagens, filas com prioridade e integração híbrida com serviços de IA.

Havia risco significativo de escopo mal definido e complexidade excessiva em uma única entrega.

## Decisão

Adotar uma estratégia de entrega faseada com 3 fases, onde cada fase entrega valor próprio e independente:

- **Fase 1 (MVP):** Upload de PDF, análise IA básica, TTS multi-voz, áudio simples, dashboard para upload/fila/configuração.
- **Fase 2:** Trilha sonora, nível de produção configurável, revisão guiada de personagens, export por capítulos.
- **Fase 3:** Modo colaborativo, múltiplos formatos de conteúdo, filas com prioridade avançada, métricas.

## Alternativas Consideradas

### Alternativa 1: MVP Completo (escopo amplo)

- **Descrição**: Entregar todas as funcionalidades de uma vez.
- **Prós**: Uma única entrega, sem necessidade de migrar entre fases.
- **Contras**: Escopo muito amplo, alta probabilidade de retrabalho, complexidade de teste multiplicada.
- **Por que rejeitada**: Risco excessivo de falha no MVP. Funcionalidades de menor prioridade (colaboração, métricas) atrasariam o核心价值 do produto.

### Alternativa 2: Backend primeiro (API sem dashboard)

- **Descrição**: Começar apenas com o backend de processamento, sem web dashboard no MVP.
- **Prós**: Backend maduro antes do frontend.
- **Contras**: Usuário sem feedback visual, sem revisão de personagens, sem colaboração no MVP. Backend sozinho não entrega valor ao público final.
- **Por que rejeitada**: O público-alvo inclui uso pessoal, que depende de interface visual para upload, acompanhamento e revisão.

## Consequências

### Positivas

- MVP entregue em tempo reduzido, com valor verificável.
- Feedback do usuário obtido antes de investir em funcionalidades de menor prioridade.
- Base de código construída uma vez, reutilizada em todas as fases.
- Risco distribuído — falhas são contidas dentro de uma fase.

### Negativas

- Dependência entre fases — a Fase 2 precisa do pipeline da Fase 1.
- Necessidade de manter compatibilidade entre versões durante a transição.

### Riscos

- **Risco**: Fase 1 pode ser tão ampla que se assemelha ao MVP Completo.
- **Mitigação**: Aplicar YAGNI rigorosamente — incluir apenas o essencial para o pipeline funcionar do upload ao áudio simples.
