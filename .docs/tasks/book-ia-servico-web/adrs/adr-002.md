# ADR-002: Stack Tecnológica — FastAPI + HTMX + PostgreSQL + Celery/Redis

## Status

Aceito

## Data

2026-05-25

## Contexto

O Book-IA migra de um console Delphi para um serviço web. A aplicação é intensiva em I/O: chamadas a APIs de IA (LLM, TTS, MusicGen), processamento de PDF, geração de áudio via Celery tasks. A escolha do stack impacta diretamente performance, velocidade de desenvolvimento e manutenibilidade.

## Decisão

Adotar o seguinte stack tecnológico:

- **Backend API:** FastAPI (Python 3.13+) — assíncrono, tipagem automática, documentação Swagger/OpenAPI integrada
- **Frontend:** HTMX + Jinja2 templates — renderização no servidor, sem necessidade de frontend JavaScript separado
- **Banco de dados:** PostgreSQL com SQLAlchemy 2.0 ORM + Alembic para migrações
- **Filas de processamento:** Celery + Redis — processamento assíncrono para TTS, IA e MusicGen
- **Armazenamento de arquivos:** Sistema de arquivos local com pastas configuráveis (PDFs, áudios, logs)
- **Autenticação:** Session-based com cookies HTTP-only (via `fastapi-session` ou `itsdangerous`)
- **Extração de documentos:** Módulo Python interno com suporte multi-formato: PyMuPDF (PDF), ebooklib (EPUB), leitura direta (TXT)

## Alternativas Consideradas

### Alternativa 1: Flask + React (Vite)

- **Descrição**: Flask para API + React separado para frontend
- **Prós**: React tem ecossistema maior; separação clara frontend/backend
- **Contras**: Dois projetos para manter; complexidade de deploy; comunicação via JSON apenas; mais boilerplate para autenticação
- **Por que rejeitada**: HTMX entrega o que precisamos (interatividade via AJAX/hx-* attributes) com menos complexidade. O MVP não precisa de SPA.

### Alternativa 2: Django + Django REST Framework

- **Descrição**: Framework completo com ORM, admin, autenticação
- **Prós**: "Batteries included"; admin panel pronto; autenticação robusta
- **Contras**: Mais pesado; menos flexível para async; ORM Django vs SQLAlchemy trade-off; curva de aprendizado maior para a equipe
- **Por que rejeitada**: FastAPI oferece melhor performance para I/O-bound (IA APIs, TTS). O Django admin é útil mas não justifica o overhead para este projeto.

### Alternativa 3: Django REST + Next.js

- **Descrição**: Next.js full-stack com API routes para FastAPI
- **Prós**: Stack moderna; SSR/SSG; bom para SEO
- **Contras**: Overkill para um dashboard interno; necessidade de Node.js + Python; deploy mais complexo
- **Por que rejeitada**: Dashboard interno não precisa de SSR. HTMX é mais simples e suficiente.

## Consequências

### Positivas

- FastAPI gera documentação Swagger automaticamente (útil para testes e integração).
- HTMX elimina a necessidade de React/JS bundle, simplificando build e deploy.
- Celery/Redis permite processamento paralelo de TTS/IA com retry automático.
- SQLAlchemy + Alembic traz migrações versionadas (algo que não existia no Delphi).
- Session-based auth com cookies HTTP-only é seguro e funciona nativamente com HTMX.
- Suporte multi-formato no MVP amplia utilidade desde o início.

### Negativas

- Redis é uma nova dependência de infraestrutura.
- HTMX tem curva de aprendizado para quem só conhece React.
- SQLAlchemy tem curva de aprendizado para quem vem do Delphi (PadraoDAO/Devart).
- Celery adiciona complexidade de deployment (worker + Redis broker).

### Riscos

- **Risco**: Redis pode falhar e impedir processamento.
- **Mitigação**: Health check no Redis; fallback para fila simples (memory-based) em caso de indisponibilidade.
- **Risco**: PyMuPDF/ebooklib podem ter conflitos de dependência.
- **Mitigação**: Ambiente Python isolado (venv); versionamento pinado em requirements.txt.
