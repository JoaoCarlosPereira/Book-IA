# ADR-004: Arquitetura do Sistema — Backend API + Frontend HTMX em Monorepo Python

## Status

Aceito

## Data

2026-05-25

## Contexto

O Book-IA precisa de um backend API REST e um frontend web dashboard. A decisão é como estruturar esses dois componentes no mesmo projeto Python, considerando simplicidade de deployment, manutenção e desenvolvimento.

## Decisão

Estruturar o projeto como um monorepo Python único com a seguinte estrutura:

```
Book-IA/
├── backend/
│   ├── app/
│   │   ├── main.py                  # FastAPI app entry point
│   │   ├── config.py                # Settings (env vars)
│   │   ├── api/                     # Routers (livro, auth, config, task)
│   │   │   ├── v1/
│   │   │   │   ├── livros.py
│   │   │   │   ├── auth.py
│   │   │   │   ├── configuracoes.py
│   │   │   │   └── tarefas.py
│   │   ├── models/                  # SQLAlchemy models
│   │   ├── schemas/                 # Pydantic schemas (request/response)
│   │   ├── services/                # Regras de negócio
│   │   │   ├── pdf_processor.py     # PyMuPDF + ebooklib
│   │   │   ├── ia_analyzer.py       # LLM analysis
│   │   │   ├── tts_engine.py        # TTS chunking + API
│   │   │   └── musicgen.py          # MusicGen API
│   │   ├── db.py                    # SQLAlchemy session factory
│   │   └── deps.py                  # Dependency injection
│   ├── templates/                   # Jinja2 templates (HTMX)
│   │   ├── base.html
│   │   ├── login.html
│   │   ├── dashboard.html
│   │   ├── livro/
│   │   │   ├── detail.html
│   │   │   ├── upload.html
│   │   │   └── review.html
│   │   └── partials/                # HTMX partials
│   ├── static/                      # CSS, JS, imagens
│   ├── celery_worker.py             # Celery app + tasks
│   ├── requirements.txt
│   ├── alembic.ini
│   └── alembic/
│       ├── env.py
│       └── versions/
├── tests/
│   ├── test_api/
│   ├── test_services/
│   └── test_celery/
├── scripts/
│   └── seed_data.sql                # Dados iniciais (vozes, admin)
└── docker-compose.yml               # FastAPI + Celery + Redis + PostgreSQL
```

### Comunicação
- Frontend (HTMX) chama endpoints da API via `hx-get` / `hx-post`.
- Celery tasks são disparadas via endpoint de API (`POST /api/v1/livros/{id}/processar`).
- Progresso é lido via polling (`GET /api/v1/livros/{id}/progresso`) ou Server-Sent Events (SSE).

### Deploy
- **MVP:** Docker Compose com 4 containers: backend, celery worker, redis, postgres.
- **Fase 2+:** Opcional: Docker Compose com nginx para reverse proxy.

## Alternativas Consideradas

### Alternativa 1: Backend API separado + Frontend React

- **Descrição**: FastAPI em porta 8000 + Vite/React em porta 3000, deploy separado
- **Prós**: Separação clara; frontend mais rico
- **Contras**: Dois builds; CORS management; deploy mais complexo; HTMX já cobre interatividade
- **Por que rejeitada**: HTMX + Jinja2 é suficiente para o dashboard do MVP. React seria overkill.

### Alternativa 2: Microserviço de PDF

- **Descrição**: Serviço Python separado para extração de PDF, chamado via HTTP
- **Prós**: Isolamento de dependências (PyMuPDF não afeta o backend)
- **Contras**: Mais componentes; deploy mais complexo; overhead de rede
- **Por que rejeitada**: PyMuPDF e ebooklib são bibliotecas leves. Isolamento não justifica complexidade no MVP.

## Consequências

### Positivas

- Um único projeto Python para manter.
- Deploy com um único `docker-compose up`.
- Templates Jinja2 funcionam nativamente com HTMX (partial renders via hx-target).
- Celery tasks no mesmo projeto acessam os mesmos models e schemas.

### Negativas

- Acoplamento entre backend e templates (menos separação de responsabilidades).
- Frontend não pode ser reutilizado por outros clientes (mobile, etc.) sem um JS frontend separado.

### Riscos

- **Risco**: Celery + FastAPI no mesmo container pode competir por recursos.
- **Mitigação**: Container separado para celery worker (mesmo código, processo diferente).
